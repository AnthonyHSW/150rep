# Syncing workouts and photos to the database

How to take workout sessions — including their exercises, sets, and photos — from the
on-device SwiftData store and persist them server-side.

## Where things stand

| Data | Lives in | Persisted? |
|---|---|---|
| `WorkoutSession`, `ExerciseLog`, `ExerciseSet` | SwiftData only | **No** |
| Workout photo JPEGs | `Documents/WorkoutPhotos/` + Supabase Storage (`workout-photos`) | Yes |
| Workout photo metadata | `public.workout_photos` | Yes |
| Attendance, crowd reports | `public.user_data`, `public.crowd_reports` via FastAPI | Yes |

The photo half is already built. `WorkoutPhotoSyncService` uploads each JPEG to Storage and
inserts a row into `workout_photos`, stamping `uploadedAt` only after both succeed so an
interrupted run retries cleanly. What's missing is the workout itself: `workout_photos.session_id`
is a bare `uuid` with no foreign key, because there is no sessions table for it to point at.
`workout_photos.sql` says so explicitly.

So this work is **a new schema plus a new sync service**, not an extension of the photo path.

## Decision: put workouts in Supabase directly, not behind FastAPI

The project has two server-side paths against what appears to be one Postgres instance:

- **FastAPI** (`api.py`, `database.py`, `query.py`) — integer `public.users.id`, resolved from
  the Supabase UUID by `get_or_create_user_id`. Enforces the `@uci.edu` rule in Python.
- **Supabase PostgREST + Storage** — `auth.users.id` UUID, enforced by row-level security.

Workouts should go the **Supabase route**, matching photos.

Reasons: the photos they belong to are already there, so `session_id` can become a real foreign
key with a cascade instead of a dangling uuid; the client already holds an authenticated Supabase
client, so there is no new endpoint, serializer, or auth plumbing; and RLS gives per-row ownership
without the UUID→integer translation step. Routing workouts through FastAPI instead would leave a
workout in one user-identity space and its own photos in another, which is the thing to avoid.

The cost is that the `@uci.edu` rule has to be restated as a policy predicate rather than inherited
from `get_authenticated_user_id`. Step 3 does that.

---

## Step 1 — Schema

New file, `workout_sync.sql`, run in the Supabase SQL editor.

Primary keys are **supplied by the client**, not generated by the database. The SwiftData models
already carry stable `UUID` ids, and reusing them is what makes re-syncing idempotent: every write
is an upsert on a key the device already knows, so a retry after a partial failure overwrites
instead of duplicating.

`user_id` is denormalized onto every table rather than joined back through the session. That's the
same call `workout_photos` made, and for the same reason — it keeps each RLS policy a direct
comparison instead of a subquery against a parent table.

```sql
create table if not exists public.workout_sessions (
    id uuid primary key,
    user_id uuid not null default auth.uid()
        references auth.users (id) on delete cascade,
    title text not null,
    start_time timestamptz not null,
    end_time timestamptz,
    status text not null check (status in ('active', 'completed', 'discarded')),
    notes text,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now()
);

create table if not exists public.exercise_logs (
    id uuid primary key,
    session_id uuid not null
        references public.workout_sessions (id) on delete cascade,
    user_id uuid not null default auth.uid()
        references auth.users (id) on delete cascade,
    exercise_id text not null,
    name text not null,
    primary_muscle text not null,
    image_name text not null default '',
    order_index integer not null,
    notes text,
    is_cardio boolean not null default false
);

create table if not exists public.exercise_sets (
    id uuid primary key,
    exercise_log_id uuid not null
        references public.exercise_logs (id) on delete cascade,
    user_id uuid not null default auth.uid()
        references auth.users (id) on delete cascade,
    set_number integer not null,
    set_type text not null check (set_type in ('W', 'N', 'D', 'F')),
    weight double precision,
    reps integer,
    duration_seconds integer,
    is_completed boolean not null default false,
    completed_at timestamptz,
    check (duration_seconds is null or duration_seconds >= 0)
);

create index if not exists workout_sessions_user_start_idx
    on public.workout_sessions (user_id, start_time desc);
create index if not exists exercise_logs_session_order_idx
    on public.exercise_logs (session_id, order_index);
create index if not exists exercise_sets_log_number_idx
    on public.exercise_sets (exercise_log_id, set_number);
```

`set_type` mirrors `SetType`'s raw values (`W`/`N`/`D`/`F`), and `status` mirrors `SessionStatus`.
Both are stored as the raw strings the Swift enums already encode, so no translation layer is
needed on either side. The `check` constraints are what stops a future rename on one side from
silently writing garbage.

`is_cardio` classifies the exercise log, while `duration_seconds` stores the time for an
individual set. Cardio sets can leave `weight` and `reps` null. Run `workout_cardio.sql` after
`workout_sync.sql` to apply these fields to an already-created database.

## Step 2 — Connect photos to their sessions

`workout_photos` already exists with rows in it, so adding the foreign key naively would fail on
any pre-existing photo whose session was never uploaded.

```sql
alter table public.workout_photos
    add constraint workout_photos_session_id_fkey
    foreign key (session_id) references public.workout_sessions (id)
    on delete cascade
    not valid;
```

`not valid` enforces the constraint on new and updated rows while leaving existing rows unchecked.
Nothing is deleted. Once you've confirmed every historical photo has a session row, promote it:

```sql
alter table public.workout_photos validate constraint workout_photos_session_id_fkey;
```

If that errors, orphan rows remain; find them before deciding what to do with them:

```sql
select p.id, p.session_id, p.created_at
from public.workout_photos p
where not exists (
    select 1 from public.workout_sessions s where s.id = p.session_id
);
```

This foreign key imposes a hard ordering on the client: **the session row must exist before its
photos are inserted.** Step 5 covers that.

## Step 3 — Row-level security

```sql
alter table public.workout_sessions enable row level security;
alter table public.exercise_logs    enable row level security;
alter table public.exercise_sets    enable row level security;
```

Each table gets the same shape of policy. `with check` matters as much as `using`: without it a
client could insert rows owned by somebody else, since the app supplies every column.

```sql
drop policy if exists "Users manage own workout sessions" on public.workout_sessions;
create policy "Users manage own workout sessions"
    on public.workout_sessions for all
    to authenticated
    using (user_id = auth.uid())
    with check (
        user_id = auth.uid()
        and coalesce(auth.jwt() ->> 'email', '') ilike '%@uci.edu'
    );
```

Repeat verbatim for `exercise_logs` and `exercise_sets`, changing only the policy name and table.

The `ilike '%@uci.edu'` clause is the UCI rule, restated. It matches `is_uci_email` in `api.py`:
the domain must be exactly `uci.edu`, so `someone@grad.uci.edu` is rejected by both. It sits in
`with check` only — a user who somehow has rows already can still read them, but cannot write new
ones. Note this is the first place the restriction is enforced on the Supabase path; `workout_photos`
does not currently have it, and adding the same clause there is worth doing in the same pass.

## Step 4 — Keep `updated_at` honest

Last-write-wins is the conflict policy, and the client is the writer, so the column has to be set
server-side or it just records whatever the device claims.

```sql
create or replace function public.touch_updated_at()
returns trigger language plpgsql as $$
begin
    new.updated_at := now();
    return new;
end;
$$;

drop trigger if exists workout_sessions_touch_updated_at on public.workout_sessions;
create trigger workout_sessions_touch_updated_at
    before update on public.workout_sessions
    for each row execute function public.touch_updated_at();
```

## Step 5 — Client sync service

Add `WorkoutSyncService` beside `WorkoutPhotoSyncService`, following its conventions: `@MainActor`,
offline-tolerant, local state mutated only to record what landed.

**Write order is fixed by the foreign keys** — a child row inserted before its parent is rejected:

0. flush pending deletions (Step 6) — before anything is written
1. `workout_sessions` — upsert the session row
2. `exercise_logs` — upsert all logs for the session
3. `exercise_sets` — upsert all sets for those logs
4. `WorkoutPhotoSyncService.syncPhotos(for:store:)` — unchanged, but now runs **last**

Use `.upsert(rows, onConflict: "id")` rather than `.insert`, and send each table's rows as one
batch. The photo service deliberately inserts one row at a time, because each row is paired with a
large binary upload that can fail independently. Workout rows have no such pairing: a batch upsert
is a single round trip, and because the keys come from the device, re-running it after a failure
converges rather than duplicating.

**Deletions are handled separately** — upserts only ever add or overwrite. See Step 6.

**When to sync.** Trigger on session completion, not continuously — an in-progress workout changes
on every tap, and syncing each one wastes requests and battery. A session the user discards should
be pushed with `status = 'discarded'` if it was already uploaded, and skipped entirely if it never
was.

**Track what's pending.** `WorkoutPhoto` distinguishes synced from pending via `uploadedAt`, and
`needsUpload` reads it. Give `WorkoutSession` the same pair — a `syncedAt: Date?` and a
`needsSync: Bool` — and stamp it only after all four steps above succeed. A partial sync must leave
the session pending so the next attempt completes it.

> Adding a property to a `@Model` is a SwiftData schema change. `syncedAt: Date?` is optional, so
> it migrates lightweightly with no migration plan, but it must be optional — a non-optional
> without a default will fail to open the existing store.

## Step 6 — Propagating deletions

A delete must reach the server, and the hard part is that by the time anything can sync, the
local object is gone. `WorkoutStore.discard` calls `modelContext.delete(session)` and the row
ceases to exist — if the device was offline, there is nothing left to describe what to remove.
Diffing against local state cannot recover it either: an absent row and a never-existed row look
identical.

So deletions need a **tombstone** — a small record that outlives the thing it describes.

```swift
@Model
final class PendingDeletion {
    @Attribute(.unique) var id: UUID   // the deleted row's own id
    var table: String                  // "workout_sessions" | "exercise_logs" | ...
    var storagePath: String?           // photos only; the Storage object to remove
    var requestedAt: Date
}
```

### Writing tombstones

Record one at each deletion site in `WorkoutStore`, in the same `try save()` as the delete itself
so the tombstone and the deletion commit atomically:

| Site | Tombstone |
|---|---|
| `discard(_:)` | the session, plus one per uploaded photo (for its Storage object) |
| `removeExercise(_:from:)` | the exercise log |
| `removeSet(_:from:)` | the set |
| `removePhoto(_:from:)` | the photo, carrying its `storagePath` |

**Only tombstone rows that were actually synced.** A row the server never saw needs no delete —
check `session.syncedAt != nil` for sessions and `photo.uploadedAt != nil` for photos. Exercise
logs and sets have no stamp of their own, so use their owning session's. This also means
`pruneIncompleteWork` needs no tombstones at all: it runs inside `finish`, before the session's
first sync, so the rows it drops were never uploaded.

**Children of a deleted session need no tombstones of their own.** The foreign keys from Step 1
and Step 2 cascade, so removing the session row takes its logs, sets, and photo rows with it.
That cascade is doing real work here, not just tidiness.

### Flushing them

Run before the upsert pass, oldest first:

```swift
try await supabase.from(deletion.table)
    .delete()
    .eq("id", value: deletion.id)
    .execute()
```

Delete the `PendingDeletion` row only after the request succeeds, so an interrupted flush retries.
This is safe to repeat: deleting an id that is already gone affects zero rows and still returns
success. RLS needs no change — the `for all` policies from Step 3 already cover `delete`, and
their `using (user_id = auth.uid())` clause means one user cannot delete another's rows.

### Storage objects do not cascade

This is the one that will otherwise leak silently. Deleting a session cascades the
`workout_photos` **rows**, but the JPEGs in the `workout-photos` bucket are not touched by any
foreign key — Storage is not part of that graph. They would sit in the bucket forever, counting
against quota, unreferenced.

`WorkoutStore` already solves the local half of exactly this problem: `discard` clears the
sandboxed files before deleting the session, with a comment explaining the same reasoning. The
remote half is the mirror image, which is why photo tombstones carry `storagePath`:

```swift
let paths = photoDeletions.compactMap(\.storagePath)
if !paths.isEmpty {
    try await supabase.storage.from(WorkoutPhotoSyncService.bucket).remove(paths: paths)
}
```

Batch these — one call takes an array, and a session can hold up to `WorkoutSession.maxPhotoCount`
photos. Remove the Storage objects **before** the row deletes: if the order is reversed and the
process dies in between, the path is gone from the database and the file is unreachable.

### Keep the reconciliation sweep as a backstop

Tombstones are the mechanism, but they live in the same store that a reinstall or a corrupted
container wipes. After upserting a session's children, also clear remote rows that have no local
counterpart:

```swift
try await supabase.from("exercise_logs")
    .delete()
    .eq("session_id", value: session.id)
    .not("id", operator: .in, value: localLogIDs)
    .execute()
```

Sets removed from a *surviving* log need the same, keyed on `exercise_log_id`. This catches
anything the tombstones missed; it is not a substitute for them, because it only ever runs for
sessions that still exist locally — a deleted session is exactly the case it cannot see.

## Step 7 — Backfill existing workouts

Every session already on device has `syncedAt == nil` the moment the property is added, so the
normal pending path covers the backfill with no special case. Run it once on launch after sign-in:
fetch sessions where `needsSync` and `status != .active`, oldest first, and sync them in sequence.

Sequentially, not concurrently — these are the user's own rows going to one connection, and serial
writes keep the foreign key ordering intact per session without coordinating between them.

## Verifying

```sql
select s.title, s.start_time, s.status,
       count(distinct l.id) as exercises,
       count(distinct st.id) as sets,
       count(distinct p.id) as photos
from public.workout_sessions s
left join public.exercise_logs l  on l.session_id = s.id
left join public.exercise_sets st on st.exercise_log_id = l.id
left join public.workout_photos p on p.session_id = s.id
where s.user_id = auth.uid()
group by s.id, s.title, s.start_time, s.status
order by s.start_time desc;
```

Then re-run a full sync with no local changes and confirm the counts are identical. Numbers that
grow on the second run mean the upsert keys aren't being honored.

For deletions, the test that matters is the offline one: go into airplane mode, delete a synced
workout, come back online, sync, and confirm the row is gone server-side. That is the path that
fails without tombstones. Then check the bucket has no leftovers:

```sql
select name from storage.objects
where bucket_id = 'workout-photos'
  and (storage.foldername(name))[1] = auth.uid()::text
  and name not in (select storage_path from public.workout_photos);
```

Rows here are orphaned files — the Storage cleanup in Step 6 isn't running, or is running after
the row delete instead of before.

## If you'd rather route through FastAPI

Should you decide workouts belong with attendance instead, the shape changes:

- Tables key on integer `users.id`, not `auth.users.id`, and carry no RLS — `api.py` is the
  gatekeeper, exactly as `user_data` and `crowd_reports` work today.
- Add `POST /v1/workouts` taking a whole session (exercises and sets nested) behind
  `Depends(get_authenticated_user_id)`, with Pydantic models mirroring the SwiftData models.
  The UCI check comes free from that dependency.
- Write the inserts in `database.py` and the SQL in `query.py`, matching the existing split.
- Photos stay in Supabase Storage regardless — FastAPI has no file handling — so
  `workout_photos.session_id` stays a dangling uuid, since it cannot reference a table keyed on a
  different user identity. Step 2 is then impossible.

That last point is the reason for the recommendation above.
